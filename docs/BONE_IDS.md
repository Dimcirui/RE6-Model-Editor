# 人物 .mod 的骨骼 ID 分布与 CTC 物理骨占用

目的：看哪些骨骼 function id 可以放心拿来做物理骨。数据来自零售 arc（nativePC + nativePC_dlc）里全部 `plXXXy.mod`（186 个）和 `plXXXy.ctc`（40 个，
有同名 ctc 的才算"物理骨"），y=0 身体、1 右手、2 左手、3 头。重新生成：`python tools/pl_bone_ids.py`，逐模型明细在 [BONE_IDS_PL.tsv](BONE_IDS_PL.tsv)
（模型、部位、骨数、是否有 ctc、非 ctc ID、ctc ID、ctc 里有但 mod 里没有的 ID）。

"ID"指骨表（`Mod211.bone_table()`）每条记录的第一个字节，也就是 .ctc 节点和 .ccl 碰撞引用的 function id。255 是"无"，所以可用范围是 0–254。

## 先说结论

1. **ID 的作用域是单个 .mod，不是整个角色。** 每个 .mod 自己的 ID 在其内部唯一（186 个全部检查过，无重复），但身体和头可以用同一个 ID 指不同的骨：
   pl0100 身体的 120–123 是挂在脊柱(2)上的双马尾，pl0103 头模的 120–122 是挂在头骨(4)上的发片；pl0670/pl0673 同理。
   部位之间靠少数共用的"接口骨"对上：头模根骨 = 身体的 2，并带着 3、4、5、10；手模根骨 = 身体的 8（右）/13（左）。
   所以给某个 .mod 加物理骨，只需要避开**这个 .mod 自己**的 ID（并避开本部位 .ctc 已用的 ID）。
2. **零售里没有任何模型用过的 ID 一共 27 个**，这是最保守的安全集合：
   `61, 98-99, 173-174, 176, 178-179, 218-219, 221-224, 226, 228-229, 236-239, 248-253`
3. **物理骨的约定区间是 120–123、130–172、190–217、240–247（外加 75–93 里的几段）**，但这些区间不是"专用"的，见下面第二张表：
   同一个 ID 在甲模型是 ctc 模拟骨，在乙模型可能是普通骨或链的挂点。
4. 能放心占用的前提是看目标模型自己的骨表，不能只看全局范围。

## CTC 链的规律

* 链内 ID 基本连续，多为 2–3 个节点（2 节点：120..121、122..123；3 节点：130..132…），最长 8 个（pl0620 的 130..137）。
* 每条链的根节点挂在一根**非 ctc 的骨**上（链的锚点）。统计全部 ctc 的根节点父骨 ID：4 × 65、2 × 51、1 × 16、3 × 10、15 × 9、16 × 6、20 × 6、17 × 3、21 × 2，
  其余是 130、136、139、142 等同区间的骨。身体的链多挂在 2、1、15/16/17/20/21，头模的链挂在 4（也有 3、5、10）；这些骨的含义（脊柱、头、大腿）是推测。
* 有的链挂在同一区间里的一根不模拟的骨上：pl0600 的 131..132 和 133..134 挂在 130（130 是普通骨，不在 ctc 里）；pl0400 的 83..85 挂 82、87..89 挂 86、
  91..93 挂 90；pl0003/0093 的 137..138 挂 136、140..141 挂 139、143..144 挂 142。**所以同一个 ID 段里，普通骨和 ctc 骨会交错，新增链时要给链根留一个挂点位置。**
* 头模 pl0003 / pl0093 的 ctc 引用 149、150，但自己的 mod 里没有这两根骨（已知，docs/CTC_CCL.md 里提到的那两个例外）。

## 没有同名 ctc 的模型

186 个 mod 里只有 40 个有同名 ctc。其余的服装变体（如 pl0070、0170、0220、0270、0320、0370、0430…）骨表里同样有 120–123/130–161 这类物理区间的骨，
但没有自己的 ctc 文件（应该是沿用相邻服装的 ctc，规律像是 xx7→xx9、xx0 配对；未验证）。所以表里这些模型的 ID 全部算在"非 ctc"一栏，
物理骨其实是被低估的：**没有 ctc 的模型里，≥75 的 ID 很可能也是物理骨，不能当成空位。**

## 约定是怎么形成的：每个 ID 由谁"驱动"

数据里没有任何地方写着"某某区间属于某某用途"。`.mod` 只存 ID 和 256 字节的 ID→骨序号表，引擎加载时原样拷进 rModel（BH6.exe `0xf49bf0`，表在对象 +0x100，
读入时不检查任何 ID）。一个 ID 的行为由**别的资源**里谁引用了它决定：

| 驱动方 | 资源 | 引用方式 | 占用的 ID（玩家） |
|---|---|---|---|
| 身体动作 | `soft/chara/pl/.../<model>PeA` 等（rMotionList，LMT v67） | 轨道的 bone id 字节 | 0–16、18–20、22–55、60–61；特殊通道 250–253、255（根/整体，不是骨） |
| 脸部动作 | `.../pl0600FaA`（头模自己的一份动作列表） | 同上 | 100–122，部分角色还有 0、2–5、10、80–87、150–156、254 |
| 扭转辅助骨 | `soft/chara/pl/plcommon/pl_common.jex`（rJointEx，所有玩家共用） | Jnt / RefA / RefB 是 function id | 62–69（夹在 5/6、6/7、10/11、11/12、15/16、15/20、16/17、20/21 之间的扭转骨）、70–73（8、6、13、11 的衍生扭转骨） |
| 角色专属辅助骨 | pl0100.jex、pl0110.jex（各自一份，其他角色用 pl_common） | 同上 | pl0100 多 175、177（挂在 16 上），pl0110 多 220——正好是它们骨表里孤立的"非 ctc"ID |
| 链物理 | `.ctc` | 节点的 bone function id | 见前文 |
| 链碰撞 | `.ccl` | 起止骨 id | 同上 |

* 全部玩家动作里没有被任何轨道碰过的 ID（0–249）：`17, 21, 56-59, 62-73(jex), 77-79, 89, 95, 97-99, 125-129, 136-149, 157-189, 213-249`。
  工具：`python tools/pl_lmt_ids.py`（713 个玩家动作列表）。
* 动作也会写物理骨的 ID：个别过场动作（s0509、s0550、s0706、s0751、s0702rp）给 74–76、131–134、190–212 写了轨道，onc/one/ond/ona 给 130–131、133、135 写了轨道。
  所以动画和 ctc 可以同时指向同一个 ID，引擎允许这种重叠，谁的结果最终生效没有验证。
* 头、手模型有自己的动作列表和自己的 ID 表，所以 ID 在部位之间可以重复（见"先说结论"）。头模型里的 2、3、4、5、10 和手模型里的 8、13 是和身体对接用的，
  骨表记录里没有标志位（`unk` 字节在 6000 多条记录里全是 0），对接靠的是什么还没查出来。
* 与 MHWI 的对比：MHWI 里非 body 部位被限制在 150–200，在 RE6 的数据里看不到对应的东西：没有范围表，没有 ID 校验，每个部位 256 个槽位互相独立。
  能确定的只是"别和上表里的驱动方撞车"；引擎代码里有没有硬编码的特殊 ID（武器挂点、IK 用的 JointNo 等）还没查。

## 实测与结论：给 pl0600 找长的连续范围（2026-10-02，用户的 nativePC_mod 测试 mod）

用户的 pl0600.mod/.ctc：193 根骨（ID 0-23、58-60、62-74、100-252），35 条链 150 个节点，全部能被模拟（零售最多 10 条链 27 个节点），
所以骨数、链数、节点数、ID 到 252 都没有撞到上限。观察到的两个问题的原因：

1. **250–253 不稳定**：它们是身体动作里的特殊通道（250/251 缩放轨道，252/253 旋转+位置+缩放轨道，255 是整体轨道），不是真正的骨，
   ctc 关掉后动画直接把这几根骨拉走。254 在头模里由脸部动作驱动。**250–255 不能用。**
2. **删掉整个 .ctc 后 121–124 的链被拉走**：删除后生效的是零售 pl0600.ctc，它的节点是 75–76、120–123、131–134，会去驱动你模型里**同 ID 的另外几根骨**
   （120 是你 117–120 那条链的末端，121–123 是另一条链）；而且 mod 的 remap 表里残留了 `remap[75]=32`、`remap[76]=33`，指向的是 ID 66、68（扭转骨），
   所以零售的 75–76 链会去拉扭转骨。"关掉物理"请用空 ctc：`tools/data/empty.ctc`（零售 pl0200.ctc 的原字节，1 条链 0 个节点）。
   导出器已改：删掉的 ID 在 remap 表里清成 0xFF（零售 5536 个 mod 里没有一个有残留项，往返测试 188 个玩家模型一致）。

**过场里头上的物理骨乱飞也是这个机制**：动作列表里文件名以 `pl0600` 开头的有 56 个（data/event 18、data/fig 2、data/ingame 34、soft/chara/pl 2），
它们给 pl0600 写了轨道的 ID（>=56）是：`60-61, 74-76, 100-122（脸部动作）, 120, 122, 130-134, 190-212, 250-253, 255`。
过场动作作用于整个角色（身体和头模各取自己表里有的 ID），所以放在这些 ID 上的物理骨在过场里会被烘焙动画接管。你现在用的 100–249 里有 51 个落在其中：
100–122、130–134、190–212（190–212 正是零售头发链 pl0603 的 ID，头上最容易飞）。

**pl0600 上没有任何驱动方的 ID（不在 0-55、60-61、62-73 jex、74-76、100-122、120、122、130-134、190-212、250-255 里）共 126 个：**

| 段 | 长度 |
|---|---|
| **135–189** | 55 |
| **213–249** | 37 |
| 77–99 | 23（pl0620 的动作用了 74–88，别的服装不受影响） |
| 123–129 | 7 |
| 56–59 | 4（58、59 在 pl0600 骨表里已有骨） |

更保守的集合：
* 整个 pl06 系列（pl0600/0610/0620 的动作）都没碰过：`56-59, 89-99, 124-129, 140, 143, 213-249`（213–249 共 37 个最长）。
* 所有玩家的动作都没碰过：`56-59, 98-99, 218-224, 226, 228-229, 231, 233-249`（233–249 共 17 个最长）。

建议：身体和头的物理骨优先用 **135–189（55 个）+ 213–249（37 个）**，共 92 个。头和身体各有 256 个独立的槽位，但过场动作是共用的，所以两边最好别和上面的驱动 ID 撞车；
同一个 ID 在身体和头里各用一次是允许的（零售就这样做），但没必要，反而让动作侧的排查更麻烦。
注意：这是"数据里没有人驱动"的结论，没有逐个在游戏里验过；别的 mod 或 DLC 动作也可能占用。

## 身体 / 头的物理骨范围分层（假设：没有硬性范围限制，不同部位互不冲突，只要没有别的机制调用）

硬性排除（所有部位）：0–55、60–61（身体/手动作）、62–73（jex）、250–255（动作特殊通道）；头另外排除对接骨 0、2–5、10 和 254（脸部动作）。
再扣掉零售 pl0600 / pl0603 里**必须保留**的非 ctc 骨（身体 58–60、74；头 100–122）。"别的机制"指动作轨道，按来源分层（ID 以 pl0600 的 56 个动作列表为准）：

| 层 | 含义 | 身体 | 头 |
|---|---|---|---|
| T1 全局保守 | 全游戏没有任何玩家动作碰过 | 32 个，最长 233–249（17） | 34 个，最长 233–249（17） |
| T2 pl06 系列 | pl0600/0610/0620 的动作都没碰过 | 58 个，最长 213–249（37） | 60 个，最长 213–249（37） |
| T3 pl0600 | pl0600 的所有动作（含过场/事件）都没碰过 | 145 个，最长 135–189（55） | 126 个，最长 135–189（55） |
| T4 只避开基础动作 | 接受过场/事件动作会写这些 ID | 177 个，最长 75–249（175） | 157 个，最长 123–249（127） |

* T1：身体 `56-57, 98-99, 218-224, 226, 228-229, 231, 233-249`，头多 58–59。
* T2：身体 `56-57, 89-99, 124-129, 140, 143, 213-249`，头多 58–59。
* T3：身体 `56-57, 77-119, 121, 123-129, 135-189, 213-249`；头 `56-59, 77-99, 123-129, 135-189, 213-249`。身体比头多的 100–119、121 是假设脸部动作只作用于头模（没验证）。
* T4：身体 `56-57, 75-249`；头 `56-59, 74-99, 123-249`。T4 里 74–76、120、122、130–134、190–212 在过场/事件/QTE 动作里会被烘焙动画接管（头上最明显）。

## 按角色 / 服装 / 部位整理（过场、事件、QTE 动作占用的 ID 一律排除）

命名 `plXXzy.mod`：XX 角色，z 服装，y 部位。`cs_plXXzy` 是过场专用的高精度模型（`data/event/face/plXX/cs_plXXzy.mod`，另有一套骨骼），
它们的动作列表（`cs_plXXzy_000`）不属于游戏里的 plXXzy，不计入。排除规则见 `tools/pl_free_ids.py`；结果见 [BONE_IDS_FREE.md](BONE_IDS_FREE.md)
（每个模型的完整可用 ID 段）和 [BONE_IDS_FREE.tsv](BONE_IDS_FREE.tsv)。要点：

* 每个模型的可用 ID = 去掉 0–55、60–73、250–255、254、（头）0/2–5/10、该模型自己的非 ctc 骨、该服装名下**所有**动作列表（基础、脸部、过场、事件、QTE、figure）用到的 ID。
  零售 ctc 驱动的物理骨不扣（可以删掉重做）。
* 没有自己名下动作列表的服装（pl0070、0120、0170、0270、0370、0430、0470、0540、0550、0570、0670、0800、9900、9910、9920，及其头）借用整个角色 XX 的动作并集，偏保守。
* 在**每个**身体 / 头里都没有被驱动的 ID：身体 `98-99, 218-219, 221-224, 226, 228-229, 236-249`（25 个）；头 `56-59, 98-99, 218-224, 226, 228-229, 231, 233-249`（34 个）。

## 没有验证的

* 引擎侧没查完：没有找到"function id → 骨"的查表代码（rModel +0x100 的表在 BH6.exe 里没有按 `[reg+idx+0x100]` 直接读取的位置），所以"引擎不校验 ID"
  只是加载代码和数据两方面都没看到校验，不是读过全部使用点的结论。
* 没有在游戏里测过任何新增的物理骨。
* 骨的含义（马尾、裙摆等）是从父骨和数量规律推断的，不是命名数据。
* 数据来自用户安装目录里的 arc；该目录装过 mod，如果某个 arc 被改过，统计里会混进去（pl0520.ctc 有两个不同内容，取了先找到的那份）。
